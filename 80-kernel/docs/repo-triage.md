# Триаж репо-эстейта (PR / issue по личным репо)

> **Единственный владелец процедуры (INV-2).** Вызывается шагом «Триаж» повестки `strategize-agenda.md` — уровень `[W]`, то есть в каждый день стратегирования. У автора был отдельным скиллом `/triage` и поглощён ритуалом стратегирования.
>
> **Почему поглощён.** Возражение против превращения в шаг было — другая alpha (холархия систем, не реестры vault), durable-дом состояния в GitHub-issues, работа механическая. Возражение верное по существу и неверное по последствию: стоя отдельной процедурой в очереди дня стратегирования, триаж копил долг. Разрешение — метод остаётся отдельным (этот файл), а **шумный обход уходит субагенту в фоне с начала сессии** и возвращается сводной таблицей к моменту шага. Механическая часть перестаёт занимать окно, диалоговая (ратификация) остаётся в ритуале, где ей и место.

Тон инженерный (INV-16). Выход прохода питает отбор задач (повестка, шаг 9).

## Scope — какие репо

Личные репо, где вы коммитите. Состав держит ваш реестр клонов (например, `CLAUDE.md` в корне клонов `.repos/` — ADR-0030); свериться с ним на старте — здесь список не дублируется (OwnerIntegrity).

- **В обходе:** личные `<owner>/*` — ваши инструменты, инфраструктура, dotfiles, сам vault.
- **Вне обхода:** сторонние read-only клоны (не наши), worktree-дубли (ветка того же репо, не отдельный репо), корпоративные (другой хост, свой workflow через трекер работодателя, иная политика атрибуции).

## Процедура

0. `gh auth status` — доступ есть. Нет → остановиться, не обходить (auth failure = сказать владельцу).
1. **Sweep (делегируемо).** Шумный fan-out по репо — суб-агент возвращает сводную таблицу, не дампы. По каждому репо scope:
   - `gh pr list --repo <owner>/<repo> --state open` (включая dependabot) + `gh pr checks` на CI-статус;
   - `gh issue list --repo <owner>/<repo> --state open`.
   Свести в одну таблицу: репо · тип (PR / issue / dependabot) · заголовок · возраст · CI · #.
2. **Категоризация → род → действие-кандидат** (аналог карты родов `inbox-triage.md`, но объекты — репо-сущности):

   | Объект | Действие-кандидат |
   |--------|-------------------|
   | dependabot PR · CI зелёный · patch/minor | → **merge** (сквош) |
   | dependabot PR · major / CI красный / breaking в changelog | → **hold**, риск разобрать отдельно (кандидат в задачу) |
   | issue-баг/фича · брать сейчас | → **задача проекта**: активно → карточка по `task-discipline.md`; не сейчас → строка в `6-tasks/backlog.md` |
   | issue протухший / неактуальный | → **close** с комментарием |
   | свой PR недоделанный | → добить / закрыть осознанно |
   | шум / дубль | → **close** |

3. **Ратификация — живой диалог (INV-2).** Таблица «объект → рекомендация» владельцу; решает он. Ни мержа, ни close односторонним выводом агента (агент — писарь метода, приоритет за владельцем). Исключение — стоячая авторизация владельца на конкретный класс (напр. «dependabot patch с зелёным CI мержи без спроса»), если он её даст; живёт она в приватной памяти `70-memory/`, а не здесь.
4. **Исполнить ратифицированное:**
   - **merge** → `gh pr merge --squash` (линейная история). Зелёный CI до мержа. Репо с «require up to date» → цикл по одному: `gh pr update-branch` → watch CI → merge (слил один → остальные снова BEHIND). PR, трогающий `.github/workflows/**`, требует у токена scope `workflow` — проверять `gh auth status` до мержа. На ошибку мержа (напр. 502) — **сверяйся с HEAD `main`, не ретрай вслепую**: 502 бывает ложноотрицательным — коммит приземлился, PR остался open → закрыть как доставленный.
   - **close** → `gh issue/pr close` + человеческая строка-обоснование, не стена текста (краткость площадки).
   - **Кандидат в задачу** → увести по `task-discipline.md` (бэклог или карточка). Durable-трекинг остаётся в issue репо — в vault не дублировать.
   - **security-relevant** (CVE-бамп, уязвимость) → пометить приоритетом для отбора задач (шаг 9 той же сессии).
5. **Хвост в отборе задач.** Кандидаты прохода = вход в шаг 9 повестки. Персистентный артефакт триаж не плодит (INV-3): его следы — состояние в самих репо + строки бэклога.

Не делать: обход корпоративных репо, авто-мерж/close без ратификации или стоячей авторизации, дубль issue-трекинга в vault, тяжёлую субагент-верификацию (личный эстейт, не платформа).
