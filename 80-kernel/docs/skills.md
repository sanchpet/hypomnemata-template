# Скиллы системы — каталог и сценарии

> Что есть, когда звать, как вызвать. Сами скиллы — `.claude/skills/<имя>/SKILL.md` (правка только там, OwnerIntegrity; этот файл — обзор, не дубль логики).

## Как вызывать

- **Вручную:** `/<имя> [аргументы]` в чате (напр. `/verify code 80-kernel/scripts/orz-check.sh`).
- **+авто:** модель зовёт сама, когда контекст подходит (помечены «+авто»); вручную тоже можно.
- **ОРЗ-ритуалы — всегда вручную:** это твой осознанный жест открытия/закрытия, модель их не запускает (`disable-model-invocation: true`).

## Откуда берутся скиллы (два дома)

Граница между домами — **переносимость**, а не полезность.

**В vault (`.claude/skills/`)** — всё, что читает топологию vault: `10-governance/`, `30-knowledge/`, scaffolds, инварианты INV, номера ADR. Вне этого дерева такой скилл не запустится, поэтому и живёт здесь: `/open` `/close` `/checkpoint` `/strategize` `/for-review` `/task-new` `/domain` `/archgate` `/fpf` `/skill-add` `/digest`.

**В маркетплейсе плагинов** — то, что работает в любом репозитории (мышление, верификация, тон, окружение). Автор держит такие скиллы в собственном маркетплейсе и подключает через `extraKnownMarketplaces` в `.claude/settings.json`; ставятся они `/plugin install <имя>@<маркетплейс>`, порядок — `/skill-add`. В шаблоне `/think` и `/verify` лежат **локальными копиями** в `.claude/skills/`, чтобы шаблон был самодостаточен; вынести их в свой маркетплейс — ваше решение.

Правило выбора дома: скилл, который знает о реестрах, Стеле или scaffolds, — в vault; скилл, который пригодится в чужом репо, — в маркетплейсе. Скилл, несущий личные данные (например, профиль вашего голоса для переписывания текстов), публичным быть не может: держать его в приватном маркетплейсе.

## ОРЗ-ритуалы (Открытие → Работа → Закрытие)

| Скилл | Масштаб | Когда | Что делает |
|-------|---------|-------|------------|
| `/open` | день | утром | утверждение плана, свёрстанного вчерашним `/close`; активные задачи с остатком; слот саморазвития; календарь (опц.); DayPlan; зеркало работ в приборе (опц.); session log |
| `/checkpoint` | сессия | конец рабочей сессии | Quick Close: коммит, capture, «Осталось» в карточке задачи (INV-9) |
| `/close` | день | вечером | итоги в session log, слот, рабочие продукты дня (предъявляются владельцу), capture-маршрутизация знания, выносы на стратегирование, факт по задачам, DayPlan в архив, план на завтра, commit |
| `/strategize` | неделя · юнит · спринт | **день стратегирования** из `config.md` | один ритуал, **режим вычисляется** из `sprint_epoch` и наличия артефактов, печатается и подтверждается (ADR-0037). Три такта: факты (агент) → сольный проход по повестке (владелец) → разбор (вдвоём). Повестка `strategize-agenda.md`: уровень `[W]` на всякой сессии, `[U]` на чётной неделе юнита, `[S-итог]` на 12-й неделе спринта, `[S-план]` в разгрузочную, `[Y]` в первую разгрузочную года. Бюджет 45 / 90 / 135 / 180 мин. Выход: `WeekReport` всегда, сверх того `UnitReport`+`UnitPlan` · `SprintReport` · `SprintPlan`+цели года |
| `/for-review` | по ходу | всякий раз, как решено «рассмотреть на стратегировании» | строка в лоток каденции (`7-plans/review/<period>-forreview.md`; каденции две — юнит и спринт). **Model-invocable** — вызывается сам, без участия владельца; каденцию при неочевидности спрашивает |
| `/digest` | по ходу | владелец просит «сохрани беседу» | выжимка ключевых идей беседы в `00-inbox/conversations/` — вход «разговор с агентом» творческого конвейера; слова владельца дословно, вклад агента помечен, транскрипт не кладётся. **Model-invocable** |

## Помощники: мышление и качество (+авто)

> Линейка: **`/think`** (как рассуждать) → **`/archgate`** (оценить архрешение) → **`/verify`** (проверить результат). Опора на принципы из `.principles` через **`/fpf`**.

| Скилл | Когда звать | Сценарий |
|-------|-------------|----------|
| `/fpf` | нужно обоснование принципами, проектирование, различение понятий | `/fpf сравнение вариантов хранилища секретов` → грузит применимые ZP/FPF/SPF + локальные инварианты, переводит термины в инженерный язык. MCP `mim-knowledge` — опционально (учётка МИМ); без него работает по локальным `.principles/` |
| `/think` | сложный выбор, несколько гипотез, риск якорения на первой идее | `/think выносить ли логику из шлюза` → ADI-цикл: гипотезы → логика → evidence (F-G-R) → bias-audit → решение |
| `/archgate` | новое архрешение, инструмент, вложенный репозиторий/MCP/хук, смена топологии — ДО записи ADR | `/archgate добавить кэш-слой` → 2 вопроса → профиль ЭМОГССБ → вето-фильтр → (прошёл) ADR |
| `/verify` | проверить готовый результат по эталону (closed/open-loop; trivial не требует) | см. ниже |

### `/verify` — как пользоваться

`/verify [тип] [путь или T-id]`. Свежий суб-агент проверяет **результат** по эталону, не видя историю создания (context isolation — не якорится на твоих рассуждениях), и возвращает вердикт PASS / CONDITIONAL / FAIL с таблицей несоответствий.

| Команда | Что проверит |
|---------|--------------|
| `/verify code <путь>` (или по `git diff`) | качество кода: логика, edge cases, секреты/PII, coupling, тесты. Скрипты vault И код повседневной работы в любом репо |
| `/verify task T-NNN` | приёмка задачи: артефакт против критериев done из карточки (модель суб-агента по `verification_class`) |
| `/verify chain` | data-flow (CoVe): прочитаны ли потребители изменённых функций, совпадают ли контракты |
| `/verify adversarial` | pre-mortem: где сломается в проде, что не прочитано, не подогнан ли scope под вывод |
| `/verify` (пусто) | автоопределение по аргументу/контексту |

Решение принять / исправить / отклонить вердикт — за тобой; спорный вердикт не продавливается.

## Создание знания

| Скилл | Когда | Что делает |
|-------|-------|------------|
| `/task-new <имя>` | проект нарезается на задачи либо появилось отдельное действие под живой проект | проверка рода (задача ≠ проект ≠ процесс, трассировка до проекта) → номер → карточка из scaffold в `10-governance/6-tasks/` с ролью, методом и бюджетом. Одна self-contained карточка, доску собирает `index`. Работы в прибор — только при взятии в юнит и только если прибор ведётся |
| `/domain <область>` | формализуешь предметную/доменную область по модели SPF | guided-flow: тест домен≠тема → имя → bounded context → scaffold паспорта в `30-knowledge/<slug>/` → дорожная карта наполнения |

## Окружение

| Скилл | Когда звать | Сценарий |
|-------|-------------|----------|
| `/skill-add <ссылка>` | принесли чужой скилл / плагин / маркетплейс Claude Code — «затащить к нам», куда положить, как обновлять, как снять | классифицировать источник (маркетплейс / плагин / голый скилл) → разведка **до** установки (триггер-поверхность `description`, самозакрепление, хуки и MCP = вето через `/archgate`) → выбрать дом (нативно user · project · dotfiles · вендоринг в vault — почти никогда) → поставить → `plugin details` (стоимость always-on / on-invoke) → контуры профилей → обновление и откат |

## Опциональные зависимости скиллов

| Зависимость | Кто опирается | Без неё |
|---|---|---|
| Super Productivity + его MCP (прибор учёта, ADR-0029) | `/open` (зеркало дня), `/close` (факт `spent_h`, слот), `/task-new` (работы в приборе), `/strategize` (носитель времени) | шаги с прибором пропускаются; факт — со слов владельца |
| MCP календаря + роли календарей в `config.md` | `/open` (шаг календаря) | шаг пропускается, открытие не блокируется |
| MCP `mim-knowledge` (учётка МИМ) | `/fpf`, `/strategize` (предзагрузка) | только локальные `.principles/` |
| `.principles/{zp,fpf,spf}` (разворачивает `repos-bootstrap.sh`) | `/fpf`, `/domain`, `/archgate`, `/think` | `/domain` не работает; `/fpf` теряет источник — развернуть первым делом |
| `week-time.py` по расписанию | `/open`, `/close` (коммит `week-time.md`) | файла нет — нечего коммитить |
