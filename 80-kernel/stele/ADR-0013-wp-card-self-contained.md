> ⚙️ **Уточнён [[ADR-0036-task-as-atomic-card|ADR-0036]].** Род «рабочий продукт» переименован в **задачу** (`WP-NNN` → `T-NNN`), а требование предъявимого артефакта **смещено по времени**: при заведении карточки он желателен, обязателен — с момента, когда задача берётся в юнит. Всё прочее в силе: карточка одна, контекст self-contained, результат предъявим. Рабочий продукт есть изменение в мире, не обязательно документ.

# ADR-0013 — Карточка РП: self-contained контекст + предъявимый артефакт

## Контекст

В предыдущей системе (IWE) контекст рабочего продукта (РП) жил во внешнем хабе, карточка ссылалась туда. После переезда в Hypomnemata эти ссылки повисли (внешний хаб — не часть нового vault). Плюс владелец зафиксировал требование: РП обязан давать **предъявимый артефакт** (изменение в физическом мире), а не быть «деятельностью».

## Решение

### 1. Контекст РП — в самой карточке (self-contained)

Весь контекст РП (постановка, метод, решения, фазы, остаток) живёт **в карточке** `10-governance/6-tasks/T-NNN-*.md` (префикс заглавный, [[ADR-0006-naming-convention|ADR-0006]]; в первой редакции — `WP-NNN`). Внешних указателей на хабы вне vault — нет.

- **Почему:** vault = единственный субстрат ([[ADR-0001-vault-as-substrate|ADR-0001]], INV-1 переносимость): чистый клон vault → весь контекст РП на месте, без внешних зависимостей.
- **Исключение — архитектура системы:** решения об устройстве самого vault не дублируются в карточке (OwnerIntegrity, INV-2) — канон в Стеле `80-kernel/stele/`, карточка ссылается (ссылка **внутри** vault, не наружу). Это касается задачи сборки самой системы; обычные задачи архитектуру vault не трогают.

### 2. РП обязан давать предъявимый артефакт

Поле `artifact:` (frontmatter) — **обязательное**: предъявимый результат, изменение в физическом мире (файл, репо, развёрнутый сервис, документ, заметка, конфиг). Не «деятельность» («отслушал», «разобрался», «поработал»).

- **Тест:** «что я могу предъявить как доказательство, что РП сделан?» Нет ответа → это не РП, а процесс (Процесс ≠ Артефакт-результат ≠ Артефакт-процесс).
- Опора: INV-14 (задача — артефакт проекта) + FPF (РП = работа с материальным выходом). Формализует требование, которое было неявным.

### 3. Шаблон РП

`80-kernel/scaffolds/task-tmpl.md` — единый шаблон: обязательные поля (id, project, direction, dissatisfaction, status, **artifact**, verification_class, budget_h, opened) + тело (постановка+трассировка / метод / критерий done / осталось) + напоминание про артефакт и self-contained. Позже поля `direction`/`dissatisfaction` сняты: родитель у задачи один — проект, старшие звенья достаются подъёмом по цепочке ([[ADR-0035-aspiration-tier-and-chain|ADR-0035]]); добавлены `role`/`method` ([[ADR-0036-task-as-atomic-card|ADR-0036]]).

## Последствия

- + Карточка переносима и самодостаточна; клон vault несёт весь контекст РП.
- + Поле `artifact` ловит «дело ради дела» на входе (пример: `artifact` исправлен с «семинар отслушан» → «учебная заметка по теме»).
- − Карточки крупных задач растут; длинные секции — под `<details>` (правило форматирования >80 строк).
- **Энфорсмент** поля `artifact` — pre-commit-гейт `task-artifact` ([[ADR-0019-pre-commit-framework|ADR-0019]]; в первой редакции `wp-artifact`); носитель сменился с ручного `hooksPath`-хука, решение в силе.

## Применение (Ф2)

Перенесённые карточки переписаны self-contained, внешние указатели на хаб предыдущей системы убраны; контекст втянут из её источников. Файлы во внешнем хабе остались бэкапом, Hypomnemata от них не зависит.
