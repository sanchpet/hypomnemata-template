# Принципы (.principles)

> Dot-зона: Obsidian игнорирует. Опорные методологические фреймворки как вложенные git-репозитории (pull-by-need референс, INV-7) + наша курация (этот файл). Upstream-контент во вложенных репозиториях не правим — только ссылаемся. Сами клоны в git vault не входят (`.gitignore`); трекается только этот файл.

## Лестница принципов

**Контракт знаний (нисходящий — обоснование и авторитет):** `ZP → FPF → SPF → паспорта доменов (30-knowledge)`. Верхний уровень обосновывает и ограничивает нижний: паспорт домена не нарушает первые принципы, первые уважают нулевые. Так знание **строится и валидируется** — сверху вниз.

| ↓ Контракт | Каталог | Что это | Upstream |
|------------|---------|---------|----------|
| Нулевые | [`zp/`](zp/README.md) | Транс-дисциплинарные ограничения (6 принципов: аксиоматичность, структурность/симметрии, многомасштабность, оптимизация, …). Дисциплинируют все остальные уровни | `https://github.com/TserenTserenov/ZP` |
| Первые | [`fpf/`](fpf/Readme.md) | First Principles Framework: мета-онтология и базовые различения (Holon, роли, мереология, ADI, F-G-R), построен на ZP | `https://github.com/ailev/FPF` |
| Вторые | [`spf/`](spf/README.md) | Second Principles Framework: как формализовать **домен** в Pack (паспорт предметной области), построен на FPF. Внутри `pack-template/` + `process/` | `https://github.com/TserenTserenov/SPF` |
| Паспорта (локальные) | — | Стела `80-kernel/stele/` (ADR + контракт) + паспорта доменов `30-knowledge/` — нижний уровень контракта | этот vault |

**Резолюция при поиске (восходящий — fallback):** конкретный вопрос решается снизу вверх — сначала самый специфичный применимый слой (паспорт / локальная Стела), при отсутствии откат к более общему (SPF → FPF → ZP). Это операционная эффективность (не пере-выводить ZP на каждый вопрос), а не направление обоснования.

## Два пути доступа (дополняют друг друга)

- **Локальные файлы** (этот каталог) — прямой `Grep`/`Read` по конкретной секции (FPF `A.7`, ZP `ZP.2`), офлайн; версия — та, что принёс последний `pull`.
- **MCP `mim-knowledge`** (опционально; `.mcp.json` в корне vault) — семантический поиск по индексированному корпусу платформы МИМ (методология + FPF/SPF): `knowledge_search` / `knowledge_get_document` / `personal_search`. Нужна учётка платформы МИМ; без неё скилл `/fpf` работает только по локальным файлам.

Скилл `/fpf` использует оба: семантический поиск через MCP → точная секция через локальный файл.

## No-Jargon: перевод FPF → инженерный язык

> Правило INV-6: в выводе каждый FPF-термин → инженерный эквивалент (в скобках или вместо). Неизвестный термин — перевести по контексту + `(FPF: <оригинал>)`.

| FPF-термин | Инженерный эквивалент | Где встретишь |
|------------|----------------------|---------------|
| Holon | Компонент с границей (часть и целое) | A.1 — декомпозиция |
| Bounded Context (A.1.1) | Контекст с чётким scope: свой язык, свои правила | DDD, микросервисы |
| F-G-R (Fact/Guess/Rumor) | Факт / предположение / слух — уровень доверия к данным | B.3 — оценка решений |
| Role ≠ Method ≠ Work (A.7) | Кто делает ≠ как делает ≠ конкретное выполнение | Проектирование процессов |
| Role Assignment (A.2.1) | Система-в-роли `система#роль:контекст`; роль сама не работает | Онтология ролей |
| Service Polysemy (A.6.8) | Сервис = обещание + роль + метод + работа + свидетельства; сервис ≠ метод | Дизайн сервисов |
| Alpha | Ключевой рабочий продукт, по которому виден прогресс | Управление проектами |
| Mereology | Отношение «часть-целое» | Архитектура, composition |
| Affordance | Что компонент позволяет делать пользователю | API, UX |
| ADI-цикл (B.5) | Гипотеза → проверка логикой → проверка данными | Принятие решений |
| Lawful Comparison (A.19) | Сравнение вариантов по одинаковым критериям | Выбор архитектуры |
| Strict Distinction (A.7) | Разные вещи — разные имена; не мешать в одном типе/enum | Code review, именование |

## Развёртывание и обновление (pull-by-need)

Лестница держится обычными вложенными клонами, а не submodule: submodule консервирует версию, и свежесть апстрима доезжала бы до второй машины только отдельным коммитом указателя ([[ADR-0038-exocortex-shims-and-nested-repos|ADR-0038]], отменяет механизм [[ADR-0017-principles-submodules-mcp|ADR-0017]]). Адреса — в реестре `REPOS` скрипта `80-kernel/scripts/repos-bootstrap.sh`.

```bash
# свежий клон vault — развернуть отсутствующее (bootstrap.sh зовёт это сам)
bash 80-kernel/scripts/repos-bootstrap.sh clone
# обновить до свежего upstream (шаг Pull-on-Touch при первом касании vault)
bash 80-kernel/scripts/repos-bootstrap.sh pull
```

Скрипт fail-open: недоступный апстрим печатает причину и не роняет работу.
