# Верификация результата

> **Принцип:** context isolation — суб-агент проверяет РЕЗУЛЬТАТ по эталону, НЕ видя историю создания (не якорится на рассуждениях автора). Архитектурное решение проверяй через `/archgate`, не здесь; захват знания — через `/close`.

Аргументы: $ARGUMENTS

## Шаг 0. Тип проверки

| Аргумент | Что проверяет |
|----------|---------------|
| `code` | Качество кода: логика, edge cases, безопасность, coupling. Скрипты/хуки vault И код повседневной работы в любом репо (натравить на `git diff`) |
| `task` | Приёмка задачи: артефакт против критериев готовности из карточки |
| `chain` | Data-flow (CoVe): прочитаны ли downstream-потребители? контракты совпадают? |
| `adversarial` | Scope & bias (pre-mortem): scope от анализа или подгонки? что НЕ прочитано? где сломается? |
| `auto`/пусто | автоопределение: `.py/.ts/.sh` → code; T-id → task; >1 файла cross-component → предложить chain; после фикса → предложить adversarial |

## Шаг 1. Собрать вход (оркестратор)

- **code:** `git diff` (или указанные файлы) + `CLAUDE.md`/конвенции затронутого репо + чеклист code.
- **task:** карточка `10-governance/6-tasks/T-NNN-<slug>.md` (критерии готовности + поле `artifact`) + сам артефакт. Модель суб-агента по `verification_class`: trivial → Haiku, closed-loop/open-loop → Sonnet, problem-framing → Opus.
- **chain:** `git diff` + `grep` всех потребителей изменённых функций/выходов + прочитать каждого.
- **adversarial:** `git diff` + список файлов, которые автор НЕ читал, но которые могут быть затронуты + описание задачи.

## Шаг 2. Запустить суб-агента (Agent, context isolation)

Спавнить Agent со входом из шага 1. **Суб-агент НЕ получает** историю сессии, задание создателя, промежуточные рассуждения — только артефакт + эталон + чеклист.

**Эталон:** code → `CLAUDE.md`/конвенции репо; task → критерии готовности из карточки; chain/adversarial → сам код. Эталон не определяется → **СТОП:** «нужен рецензент, не верификатор».

**Чеклисты:**
- **code:** логика верна? edge cases? секреты/PII/инъекции? coupling (knowledge/distance/volatility, см. справочник SOTA, если заведён в `30-knowledge/`)? тест проверяет наблюдаемый результат (не `assert True`)?
- **chain (CoVe):** (1) кто потребляет каждый изменённый выход? (2) прочитан ли каждый? (3) типы/формат совпадают? (4) переменные/env определены в scope? (5) контракт не сломан?
- **adversarial (pre-mortem):** (1) scope от анализа или подгонки под заранее выбранный вывод? (2) что не прочитано, но затронуто? (3) предположи, что сломается в проде — 3 причины; (4) альтернативные объяснения проблемы? (5) заявленный scope («1 файл», «простой фикс») = реальному?

## Шаг 3. Verdict

Суб-агент возвращает:
- **Вердикт:** PASS (0 критич., 0 высоких) / CONDITIONAL (0 критич., ≥1 высокий) / FAIL (≥1 критический).
- Таблица несоответствий: severity (критический / высокий / средний / низкий) · файл · строка · что · почему · эталон.
- Сводка по severity + рекомендация (1-3 предложения).

## Шаг 4. Показать пользователю

Вывести вердикт. Пользователь: принять / исправить по рекомендациям / отклонить вердикт с аргументом (→ обратная связь). Спорный вердикт не «продавливать» — решает пользователь.
